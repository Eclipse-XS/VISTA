# VISTA — Single Source of Truth & Data Ownership

To prevent split-brain state or silent metadata drift, every storage and compute layer in VISTA has an explicit, non-overlapping ownership boundary.

---

## 1. Authoritative Ownership Matrix

| Layer / System | Authoritative For (Source of Truth) | Mutable vs Immutable | Must NEVER Own |
|---|---|---|---|
| **Google Drive / Object Storage (`gdrive:VISTA MVTEC3D/` or S3)** | Immutable Bronze source `.tar.xz` archives; Silver per-split `.tar` shards & `transform_config.json`; committed Gold snapshot directories (`*.parquet`, `schemas.json`, `manifest.json`); quarantine manifests; remote object checksums | **Bronze:** Strictly immutable (`BronzeImmutabilityError`)<br>**Committed Gold snapshots:** Strictly immutable (`SnapshotImmutabilityError`)<br>**`LATEST_SNAPSHOT.json`:** Mutable pointer only | Pipeline run state machines, live task attempt locks, analytical SQL marts |
| **PostgreSQL 16 (`vista_metadata`)** | Operational `pipeline_runs` and `stage_runs` (with strict state-transition enforcement); canonical `samples` identities (`sample_pk`, `sample_key`); `bronze_archives` checksums; `validation_results`; raw `quality_metrics`; frozen train-only `normalization_artifacts` & `ml_normalized_features`; addressable `silver_artifacts` (`shard_relpath`, `shard_member_path`, `<shard_uri>#<member>`); `artifact_lineage`; `gold_snapshots` & `gold_exports` registry | Transactional operational state; committed `gold_snapshots`, `bronze_archives`, and `normalization_artifacts` enforce immutability on checksum drift | Large binary images, point clouds, or `.npz` BLOBs; analytical BI dashboards |
| **Gold Parquet Snapshots (`gold/mvtec_3d_ad/snapshots/<snapshot_id>/`)** | Immutable, content-addressed analytical & ML dataset versions (`contracts_v1`, `contracts_v2`); label-isolated `training_ready_samples.parquet` (`train`/`validation` only); held-out `evaluation_samples.parquet` (`test` only); frozen `normalization_artifacts.parquet`; exact `manifest.json` & `schemas.json` contracts | Strictly **immutable & read-only** after `manifest.json` commit | Live/in-flight operational stage telemetry (mutable telemetry is exported separately to `data/warehouse/telemetry/`) |
| **DuckDB + `dbt` (`data/warehouse/vista_analytics.duckdb`)** | Reproducible analytical transformations (`stg_*`, `dim_*`, `fct_*`, `mart_*`); dataset inventories, cross-category & distribution-shift marts; 97 dbt contract/leakage/grain/lineage tests; 16 analytical SQL outputs & EDA report tables | Fully **derived / rebuildable** from an explicit immutable Gold `snapshot_id` + post-publish telemetry export | Primary operational records or ML training artifact binaries (deleting `.duckdb` loses zero authoritative data) |
| **MLflow (`./mlruns/mlflow.db`)** | Experiment/run provenance linking exact `snapshot_id`, `manifest_sha256`, `data_content_digest`, `train_manifest_hashes`, `preprocessing_config_hash`, `code_provenance`, and future CV training metrics | Append-only experiment runs (shared SQLite store across `local` and optional Docker `server` modes) | Dataset binaries (no Parquet/image uploads as MLflow artifacts); operational pipeline state |
| **Local Cache (`data/{cache,bronze,silver}/`)** | Ephemeral bounded processing & hydration cache controlled by `LocalCacheBudgetManager` (`max_local_cache_gb`, `min_free_disk_gb`, worker leases, verified LRU index) | Strictly **ephemeral & disposable** after fail-closed remote verification | Authoritative copy of any dataset artifact |

## 2. Synchronization & Reconciliation Rules

1. **Bronze → PostgreSQL:** `ingest_category_to_bronze` uploads the archive to durable storage first, verifies size/MD5, and upserts `bronze_archives`, `samples`, and `file_manifests` keyed by natural keys (`sample_key`, `(layer, relative_path)`). Re-ingestion never duplicates rows or overwrites differing Bronze content.
2. **Silver → PostgreSQL:** `transform_category_to_silver` packs deterministic per-split `.tar` shards, uploads them to `silver/.../shards/<split>.tar`, records both `sha256` and `md5` in `file_manifests` and `transform_config.json`, and stores genuinely addressable `<shard_uri>#<member>` locators in `silver_artifacts` and `artifact_lineage`.
3. **PostgreSQL → Gold Snapshot:** `publish_gold_datasets` computes a deterministic `data_content_digest` over non-ephemeral dataset content (invariant to `run_id` and timestamps). If an identical `COMMITTED` snapshot exists, it is verified and reused idempotently. Otherwise, Parquet files and `schemas.json` are staged, uploaded, verified remotely (`_verify_remote_staged_artifacts`), and committed atomically by uploading `manifest.json` **last**.
4. **PostgreSQL ↔ DuckDB Operational Telemetry Reconciliation:** Because `publish_gold` cannot capture its own finished `SUCCEEDED` row inside the immutable snapshot being published, `export_operational_telemetry()` exports post-publish `pipeline_runs.parquet` and `stage_runs.parquet` to `data/warehouse/telemetry/` with an explicit `telemetry_cutoff_utc` and runs `MetadataRepository.audit_telemetry_consistency()`. Immutable dataset analytics always read the pinned Gold snapshot; operational stage analytics read the post-publish telemetry cutoff.
5. **Gold Snapshot → MLflow:** `mlflow_log_task` executes *after* `publish_gold_task` commits and records immutable tags (`vista.snapshot_id`, `vista.snapshot_manifest_sha256`, `vista.train_manifest_hashes`, `vista.code_provenance`). If MLflow is unavailable under `failure_policy=warn`, the committed Gold snapshot remains valid and unambiguous.
6. **Durable Storage → Local Cache Recovery:** `VistaMultimodalDataset` treats local `bronze/` and `silver/` strictly as a checksum-verified cache. Any missing artifact is deterministically restored from the Bronze archive or Silver `.tar` shard referenced in the immutable Gold snapshot and verified against its persisted SHA-256 before returning tensors.
